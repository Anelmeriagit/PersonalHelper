# Напоминания

Читать при правках временных и повторяющихся напоминаний, cron, Telegram-бота, привязки Telegram к аккаунту, состояния бота. Общие ограничения и карта файлов — в `PROJECT_NOTES.md`.

## Идея и данные
- Напоминания **личные**: у каждого аккаунта свои, получатель один: Telegram, привязанный к этому аккаунту. Постоянных (зашитых в код) напоминаний, поля «Кому» и общих настроек больше нет (с этапа 3b). Бот знает человека только по привязке (`tgu:<tid>` → аккаунт); имён, `whoIs`, `PERSONS` и `bot/state.json` в коде нет.
- Все ключи Redis с префиксом `DB_PREFIX` (в бою пусто). Запись по версии (CAS) через `readRec/writeRec` из `api/_lib.js`.
  - `rem:<id аккаунта>` — напоминания, формат ниже (`api/_rem.js`).
  - `bot:<id аккаунта>` — состояние бота этого аккаунта (`alias`, `pending`), см. ниже (`api/_bot.js`).
  - `tg:<id>`, `tgu:<tid>`, `tgp:<id>`, `tgt:<хеш токена>` — привязка Telegram (этап 3a); `tgs` — множество id аккаунтов с привязанным Telegram (обход для cron). Подробности ниже.
  - `cron:hb` (пульс основного запуска, время в мс, живёт 3 суток), `cron:lock` (замок запуска, `SET NX PX` 30 с), `cron:bk` (отметка «проверку копии делали недавно», 6 часов) — временные, в копию Redis не попадают (вид `cron` в `TEMP`). См. «Рассылка».
- Время везде по Москве (`Europe/Moscow`, без перехода на летнее). Часовой пояс один: Москва (решение владельца 2026-10-05).

## Запись `rem:<id>` (`api/_rem.js`)
- `custom`: массив временных `{id, date:'YYYY-MM-DD', slot:'h07'…'h23' (старые 'day'|'evening' допустимы), text, on, sent:boolean}`. `id` — 12 hex-символов. Лимит `CUSTOM_MAX` = 50, текст до 300 символов (`MAX_TEXT`), дата от сегодня до +370 дней (`MAX_DAYS`; на сайте +365).
- `recurring`: массив повторяющихся `{id, date:'YYYY-MM-DD' (дата отсчёта, первое срабатывание), every:'week'|'2weeks'|'month', slot, text, on, sent:{'YYYY-MM-DD':true}}`. Лимит `RECURRING_MAX` = 30, текст до 300, дата отсчёта от сегодня до +370 дней. Конца у повторов нет: до удаления или выключения.
- `normRem` оставляет только допустимые записи с допустимыми полями (чужое и испорченное отбрасывается при первой же записи). Читает `readRem(id)` → `{rem, etag}`, пишет `mutateRem(id, fn)`: чтение, `fn(rem)`, запись по версии, до 6 повторов при чужой записи; `fn` может вернуть `{err}`, тогда запись не делается. В обход `mutateRem` не писать.
- Слоты «после HH:00» по Москве: часовая сетка `h07`…`h23` (17 слотов; ключ `'h'` + две цифры часа, `SLOT_HOUR`, `FIRST_HOUR`/`LAST_HOUR` в `_rem.js`). Старые `day` (14:00) и `evening` (18:00) остаются допустимыми и равны `h14` и `h18`: записи не переписываются, `planRem`/`planShr` сравнивают слоты по часу (`SLOT_HOUR[it.slot] !== SLOT_HOUR[slot]`), список сортируется по дате и часу (`slotKey`). Слот вне сетки отбрасывает запись при нормализации и даёт `400 bad request`. Cron на Hobby раз в сутки, поэтому `/api/cron` вызывают ещё внешние планировщики (план — «Переход на внешний планировщик»); каждый запуск берёт час по Москве и шлёт всё, чей час уже наступил (часть 2). В `vercel.json` пока прежние два вызова (11:00 и 15:00 UTC, второй с `?slot=evening`): их заменит один ежедневный вызов в части 4. **Слоты кроме `h14` и `h18` заработают только когда `/api/cron` вызывается чаще (часть 4: QStash, cron-job.org); до тех пор их догонит ближайший из двух вызовов Vercel.**
- Расписание повторяющихся: `recDue(it, date)` — с даты отсчёта каждые 7 / 14 дней или раз в месяц в то же число; если числа в месяце нет (29–31), то в последний день месяца. `recNext(it, from)` ищет ближайшую дату (до 70 дней вперёд). Всё это живёт в `_rem.js` (`_bot.js` расписание не знает).
- `planRem(rem, now, slot)` вызывается внутри `mutateRem`: берёт временные с `date === сегодня`, `on !== false`, не отправленные, и повторяющиеся с `recDue` на сегодня; **сразу помечает** отправку (`sent`), поэтому повторный запуск cron не дублирует. Какие слоты пора слать, решает `hourDue`: `slot` задан (ручной запуск `?slot=…`) — только слот ровно этого часа, время суток не смотрим; `slot` не задан, а в `now` есть `hour` (`mskNow()` отдаёт `{month, date, hour}`) — всё, чей час уже наступил (`SLOT_HOUR[it.slot] <= hour`), то есть утреннее, пропущенное запуском, догоняется в тот же день; нет ни того ни другого (сухой прогон с `date`) — весь день. Следствие догонки: включённое позже в тот же день напоминание, чей час уже прошёл, уйдёт при ближайшем запуске. Заодно удаляет временные старше 60 дней и отметки повторяющихся старше 60 дней (только когда у аккаунта что-то уходит). `unclaimRem(rem, fails)` снимает отметку у неудавшихся отправок: следующий запуск отправит их заново. Вчерашнее неотправленное не догоняется (догонка только в тот же день).

## Общие напоминания пары (этап 5, «Соединить аккаунты», часть 4 — сервер, часть 5 — сайт)
- Принадлежат паре, а не аккаунту. Запись `shr:<меньший id>:<больший id>` (имя даёт `pairId` из `api/_acc.js`, одинаково для обоих), та же форма списков `custom` и `recurring` и те же лимиты (50 и 30 на пару), но у каждого напоминания две галочки и две отметки отправки, по одной на аккаунт. Сторона `a` — аккаунт с меньшим id, `b` — с большим (`sideOf`). Временное: `{id, date, slot, text, on:{a,b}, sent:{a,b}}`; повторяющееся: `{id, date, every, slot, text, on:{a,b}, sent:{'YYYY-MM-DD':{a,b}}}`. Новое создаётся с обеими галочками включёнными. Нормализация `normShr` (`scustom1`, `srec1`): новое поле добавлять туда в первую очередь.
- Читать только `readShr(a, b)`, писать только `mutateShr(id, pid, fn)` (как `mutateRem`: запись по версии, до 6 повторов; `fn(shr, me, other)`). Давать доступ можно только после `partnerAcc(id)`; обработчики берут запись через `target(uid, shared)` из `_rem.js` (нет связи — `null`, ответ `409 {error:'nopair'}`). В обход `mutateShr` не писать.
- Что видит сайт: `shared` в ответе `GET /api/reminders` (и в ответах `/api/custom`, `/api/recurring`) есть только у соединённого аккаунта (нет поля = не соединён): `{linked:true, name, custom, recurring}`. У каждого напоминания `on` — своя галочка, `pon` — партнёра; у временного ещё `sent`/`psent` (ушло мне / партнёру); у повторяющегося `next` считается по своей отметке. Имя партнёра `name` (может быть `''`). Id партнёра сайту не отдаётся.
- API: те же `/api/custom` и `/api/recurring`. `POST`/`PUT` с `shared: true` в теле, `DELETE` с `?shared=1`. Переключатель `PUT {id, key:'on', value, shared:true, who?:'me'|'partner'}`: `who` выбирает, чью галочку менять (по умолчанию свою; менять может любой из двоих, подтверждено владельцем 2026-10-09, `notes/account.md`); другое значение `who` — `400`. Правка общего временного: `400 past`, если оно уже ушло хотя бы одному; остальные ошибки те же. Запрос без `shared` всегда идёт в личные напоминания.
- Рассылка (`api/cron.js`, `one()`): каждый аккаунт при своём обходе забирает только свою сторону (`planShr` внутри `mutateShr`, отметка до отправки) и получает сообщение в свой Telegram (тот же текст «🔔 …»). Нет привязки Telegram — ничего не помечается. Сбой отправки снимает отметку только у этой стороны (`unclaimShr`), блокировка бота отметку оставляет. Сухой прогон считает и общие. Старые общие временные (старше 60 дней) и отметки повторяющихся (старше 60 дней) чистятся так же, как у личных.
- Разрыв связи (`unpair`, он же при удалении аккаунта) удаляет запись `shr:` у обоих; личные напоминания остаются. `joinPair` перед новой связью тоже удаляет запись этой пары (на случай, если разрыв не дочистил), чтобы старые общие напоминания не вернулись. Запись, которую успел создать запрос в момент разрыва, может остаться без пары: её никто не читает, при новом соединении этой пары она удаляется.
- Расход команд Redis: `GET /api/reminders` без связи 3 (`GET pair:<id>` добавился к `HMGET rem`, `GET tg`), со связью 6 (ещё `GET pair:<partner>`, `GET acc:<partner>` и `HMGET shr`). Cron: аккаунт без связи платит одним `GET pair:<id>` на слот; со связью ещё тремя на проверку пары и одной на чтение общей записи, записью по версии только если сегодня есть что слать. Общее создание (`POST /api/custom` с `shared`) стоит 7 команд: проверка пары 3, общая запись (чтение и запись), личная запись, `GET tg`; пара проверяется один раз, ответ собирается с готовыми `pr` и `shr` (`ctx` в `pubRem`).

## Состояние бота `bot:<id>` (`api/_bot.js`)
- `alias`: личные псевдонимы и исправления магазинов `{ключ: {c: категория, t: название для показа, at: время записи, мс}}`. Лимит `ALIAS_MAX` = 200: при переполнении вытесняются самые старые по `at` (не по порядку ключей: числовые ключи вроде `"5"` в объекте идут первыми). Ключи см. в `notes/cashback.md`. Работа: `aliasSet`, `aliasDel`.
- `pending`: ожидающие запросы с кнопками `{id (8 hex): {q: текст запроса (до 100 символов), ts, l: снимок списка категорий, f: сколько из них «заполненных», m: 'fix'}}`. Лимит `PENDING_MAX` = 50 (вытесняются самые старые по `ts`), TTL 1 сутки (`PENDING_TTL`): просроченные игнорируются при чтении и удаляются при следующей записи (`pendingPut`). Запрос с тем же текстом переиспользует id.
- Читает `readBot(id)` → `{state, etag}`, пишет `mutateBot(id, fn)` (чтение, `fn(state)`, запись по версии, до 6 повторов). `normBot` обязан перечислять все поля состояния: неперечисленное теряется при первой же записи. Новое поле: добавить в `normBot` и сюда. Состояние пишет только бот (`telegram.js`); cron сюда не пишет, а напоминания лежат отдельно (`rem:<id>`), поэтому их записи не пересекаются.

## Привязка Telegram (этап 3a)
- Человек входит на сайт → блок «Telegram» на вкладке «Напоминания» → «Привязать Telegram» → `POST /api/tglink` → ссылка `https://t.me/<бот>?start=<токен>` → «Запустить» в Telegram → бот отвечает «Готово: Telegram привязан к аккаунту «…»». Токен: 16 случайных байт в base64url (22 символа), одноразовый, живёт `LINK_TTL` = 600 с, новая ссылка гасит прежнюю. Сам токен не хранится: в Redis `tgt:<sha256(токен)[0..32]>` → id аккаунта.
- Данные (функции в `api/_acc.js`): `tg:<id аккаунта>` → JSON `{tid, chat, un, at}` (`un` — username без лишних символов, показывается владельцу на сайте); `tgu:<tid>` → id аккаунта (один Telegram — один аккаунт); `tgp:<id>` → хеш последней выданной ссылки; `tgs` → множество id аккаунтов с привязкой. Токен забирает `take` (Lua `-- take`: GET и DEL атомарно), поэтому две попытки с одним токеном не пройдут обе.
- `bindTelegram(token, from, chat)` → `{id}` или `{error:'bad'|'busy'}`; сначала `SADD tgs`, потом `SET tg:<id>`. `busy`: этот Telegram уже у другого аккаунта (токен при этом израсходован, нужна новая ссылка). Перепривязка аккаунта к другому Telegram освобождает прежний. `unlinkTelegram(id)` убирает id из `tgs`, удаляет `tg:` и `tgp:`, а `tgu:` только если он указывает на этот аккаунт; идемпотентна. `linkedIds()` отдаёт id из `tgs` (cron проверяет каждый ещё через `getLink`). `accountOfTelegram(tid)` отдаёт id аккаунта по числовому Telegram id: верит только полной паре `tgu:<tid>` + `tg:<id>` с тем же `tid`; username не используется.
- `GET /api/tglink` → `{linked, username?}` (на сайте нужен только опросу привязки, см. «Фронтенд»); `POST` → `{url, ttl}` (ошибки: `401`, `429` при больше 5 ссылок за 10 минут на аккаунт, `503` если не ответил `getMe` или Redis); `DELETE` → `{linked:false}`. Нужна сессия. Имя бота даёт `botUsername()` (`getMe`, кэш в памяти экземпляра); в коде и на сайте имени бота нет.
- Бот (`api/telegram.js`): `/start <токен>` в личном чате работает для любого человека (`onBind`); в группах тишина. Не привязанному человеку на голый `/start` приходит подсказка, как привязать; остальной текст и команды от него игнорируются. Привязанному на голый `/start` — приветствие по нику.
- Аккаунты, привязанные в 3a (до появления `tgs`), в множество не попадали: их добавляет только перепривязка (режим `--backfill` удалённого скрипта чистки больше недоступен).

## Временные
- Создаются на сайте: календарь (дата) → время (сетка кнопок «07:00»…«23:00», 17 штук, `.slots.hrs`; на карточке «после 15:00») → текст. Получатель один (привязанный Telegram).
- Карточка: текст, дата и слот, статус («Отправлено ✓» / «Не отправлено» / «Выключено»), строка «Включено» с переключателем, справа вверху карандаш (изменить) и крестик. Крестик → «Уверены?» (сбрасывается через 4 с) → удаление. Карандаш открывает ту же форму `#tmpForm` в режиме правки: дата, время и текст подставлены, кнопка «Сохранить». Карточка в правке подсвечена (`.editing`). Карандаша нет у полностью отправленных и пока открыт «Уверены?». У просроченных неотправленных карандаш есть: можно перенести на новую дату. Отправленные и просроченные остаются в списке серыми, управление отключено, удалить можно.
- Сегодняшняя дата: слот недоступен, если сейчас по Москве час ≥ часа слота (в 12:00 доступны `h13` и позже); с 23:00 сегодняшний день в календаре заблокирован. Проверяется и на сервере (`400 late`).

## Повторяющиеся
- Создаются на сайте: календарь (дата первого раза) → частота (каждую неделю / каждые 2 недели / каждый месяц) → время → текст. Правила слотов и «сегодня уже поздно» те же, что у временных.
- Карточка: текст, «Каждые 2 недели, после 14:00», «Ближайшее: дата» (`next` считает сервер в `publicRecurring`; если сегодняшнее уже ушло, то следующая дата), «Включено» с переключателем, карандаш и крестик с «Уверены?». Статуса «Отправлено» нет, карточки не «просрочиваются».
- Правка (карандаш): форма показывает ближайшую дату, частоту, время и текст. Если сменили частоту или дату, клиент шлёт `date` = показанную дату, и она становится новой датой отсчёта (иначе расписание «поедет»). `late` при правке не проверяется.

## Рассылка: `api/cron.js`
- `GET /api/cron` с заголовком `Authorization: Bearer <CRON_SECRET>` (только заголовок). Время берётся по Москве из часов: шлётся всё, чей час наступил и что не помечено (часть 2 перехода на внешний планировщик). Параметры:
  - `slot=h07…h23|day|evening` — ручной запуск ровно одного слота независимо от времени суток (мусор → `400`). Пульс не ставит.
  - `dry=1[&date=YYYY-MM-DD]` — сухой прогон: ничего не отправляет, не пишет и замок не берёт; без `date` считает то, что ушло бы сейчас, с `date` (только с `dry=1`) — весь день без учёта часа. `?send=` отвечает `400 send removed`.
  - `role=primary` (по умолчанию) | `backup` (другое → `400`). Основной (QStash) ставит пульс `cron:hb` (не при `dry` и не при `slot`). Запасной (cron-job.org и ежедневный вызов Vercel, часть 4) читает пульс (1 команда): если основной сработал меньше 15 минут назад, отвечает `200 {skipped:'primary alive'}` и ничего не делает; иначе берёт рассылку сам, `took_over:true`, пульс не ставит.
  - Замок `cron:lock` (`SET NX PX` 30 с, метка владельца, снимается в конце запуска и при ошибке, чужой замок не снимает): занято → `200 {busy:true}`. Основной ставит пульс до замка, поэтому занятый замок не делает его «молчащим».
- Ответ: `role`, `took_over` (запасной, который работает), `last` (ISO-время пульса основного до этого запуска, `null` — пульса нет или он старше 3 суток; видны и в сухом прогоне); в рассылке ещё `hour`, `slot` (если задан).
- После рассылки cron делает резервную копию Redis на оставшееся время (`backupStep`, только числа в ответе); сбой копии не отменяет отправленное, а рассылка не ждёт копию. Нет `BACKUP_KEY` — копия выключена (`backup:{state:'off'}`).
- Копия: проверка «пора ли» (`backupIfDue` ходит в список Blob, а это дорогая операция Hobby) идёт не чаще раза в 6 часов, отметка `cron:bk` (`SET NX PX`); между проверками `backup:{state:'skipped', reason:'recent'}`. Незаконченная копия (`partial`) отметку снимает: следующий запуск продолжит. Подробности — `notes/backup.md`.
- Обход: `linkedIds()` (множество `tgs`) → на каждый аккаунт `one()`: `readRem` → пробный `planRem` на копии → `partnerAcc` и, если пара есть, `readShr` и пробный `planShr` его стороны (общие напоминания, «Общие напоминания пары») → если слать нечего, конец → `getLink` (нет привязки или `chat`: `nolink`, ничего не помечается) → `mutateRem` с `planRem` (отметки ставятся до отправки) → отправка `sendCustom(chat, text)` (текст «🔔 …», без кнопок) → у неудавшихся `unclaimRem`.
- Параллельно читаются `WORKERS` = 8 аккаунтов, отправки идут общей очередью с шагом `GAP_MS` = 50 мс (около 20 сообщений в секунду; общий предел Telegram около 30). Бюджет `BUDGET_MS` = 24 с из `maxDuration` 30 с: не успевшие аккаунты считаются в `left` и добираются повторным вызовом (отметки не дадут дублей).
- Ошибка отправки с текстом `blocked|deactivated|chat not found|kicked` (`DEAD`) — человек заблокировал бота или удалил чат: отметка остаётся, повтор не нужен, считается в `blocked`. Любая другая ошибка — сбой: отметка снимается, `failed`. Шаблон `DEAD` взят по памяти и на настоящем Telegram не проверялся (`notes/CHECKLIST.md`).
- Ответ рассылки: `{date, hour, slot?, role, took_over, last, accounts, sent, failed, blocked, nolink, errors, left, backup}`; код 502, если есть `failed`, `errors` или `left` (повторите вызов; QStash повторит сам) либо копия дала ошибку (или осталась незаконченной в последнем запуске дня, час 23), иначе 200. Сухой прогон: `{dry, date, hour?, slot?, role, took_over, last, accounts, would_send, nolink, errors, left, backup}`. Поле `backup` и ручной запуск копии `?backup=1` (замка и ролей не касается) описаны в `notes/backup.md`. В ответе только числа; в журнале Vercel id аккаунтов только началом (8 символов).
- Внешнего мониторинга нет (решение владельца 2026-10-05): ошибки cron видны в журнале Vercel и по коду 502; `notifyAdmin` убран.

## API
- `GET /api/reminders` → `{linked, username?, custom, recurring, shared?}` (`shared` — общие напоминания соединённой пары, см. «Общие напоминания пары»; `linked` — привязан ли Telegram к аккаунту; `username` — @имя без `@`, может быть пустой строкой, поля нет у не привязанного; он берётся из той же записи `tg:<id>`, что и `linked`: `pubRem` читает её один раз, всего запрос стоит 3 команды Redis без связи (`HMGET rem:<id>`, `GET tg:<id>`, `GET pair:<id>`) и 6 со связью; `custom` — временные по возрастанию даты и слота, у каждого `sent:boolean`; `recurring` — по возрастанию ближайшей даты, у каждого `next`). Только GET. Ответ собирает `pubRem` из `_rem.js`.
- `POST /api/custom` с `{date, slot, text}` — создать временное. Ошибки: `400 bad request|bad date|late`, `409 limit`.
- `PUT /api/custom` с `{id, key:'on', value:boolean}` — включить/выключить (`404 gone`).
- `PUT /api/custom` с `{id, text?, date?, slot?}` (без `key`, хотя бы одно поле) — правка. Клиент шлёт только изменившиеся поля. Если `date` или `slot` реально изменились, проверки как при создании (`400 bad date|late`). Отправленное → `400 past` (переносить можно только неотправленное). Прочие ошибки: `400 bad request`, `404 gone`.
- `DELETE /api/custom?id=<id>` — идемпотентно.
- `POST /api/recurring` с `{date, every, slot, text}` — создать повторяющееся. Ошибки: `400 bad request|bad date|late`, `409 limit`.
- `PUT /api/recurring` с `{id, key:'on', value:boolean}` или `{id, text?, date?, slot?, every?}` без `key` — правка (`date` — новая дата отсчёта, проверка `400 bad date`). `DELETE /api/recurring?id=<id>` — идемпотентно.
- Все ответы `/api/custom` и `/api/recurring` — тот же объект (в том числе `username`), что у `GET /api/reminders`; на сайте он целиком заменяет `rem`. Везде нужна сессия (`401 {error:'auth'}`), ответы с `Cache-Control: no-store`, данные только аккаунта из сессии.

## Безопасность бота
- `POST /api/telegram` (`api/telegram.js`): сначала сверяет заголовок `X-Telegram-Bot-Api-Secret-Token` с `webhookSecret()` через `safeEq`, иначе `401`; группы игнорирует; `/start <токен>` обрабатывает для любого в личном чате (привязка); остальное — только для привязанного человека (`accountOfTelegram`): `/cashback`, ответ на название магазина, кнопки (`sk|so|sp|sf|sr|sb`, формат в `notes/cashback.md`, `onShopCb`). Нажатия от не привязанных и из групп молча игнорируются; после проверки всегда отвечает `200`, чтобы Telegram не повторял обновление; при сбое отвечает пользователю коротким сообщением.
- `GET /api/tg-setup`: только с `authed(req)` (`Authorization: Bearer <CRON_SECRET>`); регистрирует вебхук со `secret_token`, `allowed_updates: ['message','callback_query']`, команды (`BOT_COMMANDS`: `/cashback`, «Показать кэшбэки») и кнопку меню, `drop_pending_updates: true`.
- Секреты в `_bot.js`: `webhookSecret()` = `sha256('wh:' + токен бота)`; `authed` возвращает `false`, если `CRON_SECRET` не задан, принимает только заголовок `Authorization: Bearer`; `safeEq` сверяет длину до `timingSafeEqual`. Остаточный риск: при пустом `TELEGRAM_BOT_TOKEN` секрет вебхука становится известной константой (бот при этом не отправляет сообщения).
- Бот: `@PersonalHelper1Bot` (токен в `TELEGRAM_BOT_TOKEN`, запасное имя `BOT_TOKEN`). Смена бота: новый токен в Vercel → Redeploy → `/api/tg-setup` → каждый человек нажимает «Запустить» у нового бота (без этого Telegram не даёт ему писать). Привязка хранит числовые id человека и чата, поэтому должна сохраниться (при смене бота не проверялось).

## Переход на внешний планировщик (этап 5, план по частям; решение владельца 2026-10-10)
Цель: больше времён отправки и больше пользователей. Ограничение Hobby (cron раз в сутки) обходится внешним вызовом `/api/cron`.
- **Схема из трёх уровней:** основной — Upstash QStash (расписание каждые 10 минут, 07:00–23:59 МСК, то есть `*/10 4-20 * * *` по UTC; секрет передаётся заголовком `Upstash-Forward-Authorization: Bearer <CRON_SECRET>`; по официальной странице бесплатно 1 000 сообщений в сутки и 10 расписаний, цифры перепроверить при заведении), запасной — cron-job.org (раз в 30 минут со сдвигом, `?role=backup`), страховка — один ежедневный вызов Vercel cron (`?role=backup`). Redis держит пульс `cron:hb` (запасной пропускает запуск, если основной жив), замок `cron:lock` (`SET NX PX`, два запуска не идут одновременно) и очередь `dueq`.
- **Части:** 1 — часовая сетка слотов (сделана, см. выше); 2 — `/api/cron` по текущему времени, `role`, пульс, замок (сделана, см. «Рассылка»); 3 — индекс `dueq` в Redis (отсортированное множество «аккаунт или пара → время ближайшей отправки», пишут только `mutateRem`/`mutateShr`, cron читает только тех, кому пора; раз в сутки полный обход по `tgs` перестраивает индекс; ключ в `KNOWN` в `_backup.js` (временные `cron:hb`, `cron:lock`, `cron:bk` уже в `TEMP`, вид `cron`); скрипт заполнения в `scripts/` в сухом режиме по умолчанию); 4 — подключение планировщиков, `vercel.json` (один ежедневный вызов), заметки и `MAX_USERS`.
- **Почему индекс обязателен:** сейчас на аккаунт уходит около 2 команд Redis за слот (около 120 в месяц). При обходе всех аккаунтов каждый час с 7 до 23 это около 960 в месяц на аккаунт, при 500 аккаунтах 480 тыс. из 500 тыс. бесплатных. Без индекса частые запуски включать нельзя.
- **Порядок деплоя:** части 1–3, затем расписания во внешних сервисах. Если Redis недоступен, не сработает ни один уровень (запуск вернёт 502, отметки не поставятся, после восстановления всё уйдёт с опозданием).
