# Резервная копия Redis

Читать при правках `api/_backup.js`, запуска копии из cron (`api/cron.js`), скрипта восстановления, ключа `BACKUP_KEY`. Общие ограничения и карта файлов — `PROJECT_NOTES.md`.

## Решения владельца
Копируются все данные Redis, кроме временных (`rl`, `tgt`, `tgp`, `cnt`, `cnp`, `cron`); автоматически внутри cron раз в 7 суток (плюс ручной `?backup=1`); хранятся 7 копий (7 недель); шифрование ключом `BACKUP_KEY` (AES-256-GCM); скрипт восстановления с проверкой. Blob хранит только эти зашифрованные копии, данные пользователей в Blob не пишутся.

## Чтение ключей и формат (`api/_backup.js`)
- `readBatch(cursor, {count})` → `{recs, cursor, done, stats}`: `SCAN MATCH <DB_PREFIX>*`, типы `string`, `hash`, `set`, `zset` читаются пачками (zset — `ZRANGE 0 -1 WITHSCORES`, запись `{k, t:'z', v:[[член, счёт], …]}`, при восстановлении `ZADD`; `FORMAT` = 1, старый код восстановления такую запись не прочтёт). Другие типы пропускаются (`stats.other`); пропавший ключ — `gone`; сменивший тип между `TYPE` и чтением — `changed`. Сбой Redis или сети — ошибка наружу, пустой копии не бывает.
- Вид ключа — первый отрезок имени без префикса (`doc:<id>` → `doc`, `shr:<id>:<id>` → `shr`). `KNOWN` (вид → тип) читается **одной командой** на ключ (`GET`, `HGETALL`, `SMEMBERS`, `ZRANGE`) без `TYPE` и `PTTL`, срока жизни у таких ключей нет: `string` — `acc`, `nick`, `tg`, `tgu`, `users`, `gid`, `pair`; `hash` — `doc`, `rem`, `agent`, `wifi`, `bot`, `shr`, `wfs`; `set` — `tgs`; `zset` — `dueq` (производный индекс, восстанавливается и перестройкой). `TEMP` (`rl`, `tgt`, `tgp`, `cnt`, `cnp`, `cron`: `cron:hb`, `cron:lock`, `cron:bk`, `cron:rb`) не копируется, число идёт в `stats.temp`. Неизвестный вид читается дорогим путём (`TYPE` и `PTTL`, срок сохраняется); так же — известный ключ, ответивший `WRONGTYPE`.
- **Новый вид ключа добавлять в `KNOWN` (если срока жизни нет) или в `TEMP`**; если у известного вида появится срок (`EX`/`PX`), убрать его из `KNOWN`, иначе срок в копию не попадёт.
- При пустом `DB_PREFIX` (бой) ключи тестового проекта (`SKIP_PREFIXES`: `t:`, `selftest`) пропускаются (`stats.foreign`).
- Запись `{k, t:'s'|'h'|'e'|'z', v, ttl?}`: ключ без префикса (копию боя можно развернуть в `t:`), hash парами `[[поле, значение]]`, `ttl` — оставшиеся миллисекунды.
- Шифрование: `seal`/`open`, файл `PHB1` | id ключа (4 байта sha256) | iv (12) | тег (16) | шифртекст, новый iv на часть; заголовок и `snap|n` входят в AAD (часть нельзя переставить в другую копию). `BackupError.kind`: `config` (нет или слабый ключ), `format`, `key` (другой ключ), `tamper`, `missing`, `busy`.
- `BACKUP_KEY`: ровно 64 hex-символа, не менее 8 разных. Потеря ключа = копии не расшифровать; смена делает старые нечитаемыми (список покажет `error:'key'`).
- Часть = `encodePart({snap, n, recs})` = gzip(заголовок `{v,snap,n,at,prefix,count}` + запись на строку) → `seal`; `decodePart` проверяет шифр, версию, номера, форму записей, их число и предел распаковки `MAX_PLAIN` (64 МБ). `restoreCmds(rec, префикс)`: `DEL`, затем `SET`/`HSET`/`SADD`/`ZADD`, затем `PEXPIRE`.
- SCAN не атомарен: ключ, записанный во время обхода, попадёт в старой или новой версии; повторы возможны, при восстановлении побеждает последняя запись. Документы версионируются (CAS), поэтому копия ключа сама по себе целостна.

## Хранение в Blob
- Только здесь в `api/` используется Blob (`import('@vercel/blob')` при первом обращении). Приватный доступ, всё зашифровано, открыты только имена файлов. Раскладка (`backup/`, для проверок `BACKUP_DIR`): `backup/<копия>/p<n>.bin` (части; `PART_BYTES` = 1 МБ открытого текста), `backup/<копия>/manifest.bin` (зашифрованный JSON: `v`, `snap`, `at`, `end`, `prefix`, части `{n, bytes, count, sha}`, `keys`, `bytes`, `stats`), `backup/progress.bin` (ход). `<копия>` = `20261005t180000-ab12` (UTC до секунды и 4 hex; по алфавиту = по времени; две копии в одну секунду упорядочиваются случайно — при раз в неделю неважно).
- Копия полна, только когда записан манифест (последним). `runBackup({budgetMs, count, partBytes, keep, now})` → `{state:'done', snap, parts, keys, bytes, stats, pruned}` | `{state:'partial', snap, parts, keys}` (бюджет `BUDGET_MS` = 22 с кончился, повторить) | `{state:'busy'}`; ошибки выбрасываются.
- Ход `progress.bin` (AAD `progress`): `{snap, at, upd, cursor, done, n, parts, stats}`, пишется после каждой части; он же замок (`allowOverwrite:false`, обновление с `ifMatch`). Моложе `LEASE_MS` = 45 с — занято; старше — продолжается с курсора. Старше `STALE_MS` = 3 суток бросается вместе с частями (незаконченная копия доделывается ближайшими запусками cron). Нечитаемый ход заменяется; если манифест уже записан, а ход остался, ход удаляется и копия начинается заново. Сбой записи части ход не двигает.
- Ротация `pruneBackups(keep = 7)` (`KEEP`) в конце удачной копии: остаются `keep` новейших полных (не меньше одной), прочие и неполные чужие ходу удаляются; чужие файлы не трогаются; копии под старым ключом считаются в 7. `listBackups()`, `readManifest(snap)`, `readPart` (проверяет размер и sha, потом шифр), `verifyBackup(snap)` → `{ok, snap, parts, keys, problems}` (без содержимого).

## Запуск из cron (`api/cron.js`)
- Копия идёт из каждого запуска `/api/cron` после рассылки на оставшееся время: бюджет обхода `min(20 с, 30 с − потрачено − 8 с запаса)`, меньше 3 с — `{state:'skipped', reason:'time'}`. Проверка «пора ли» (`backupIfDue`, ходит в список Blob) не чаще раза в 6 часов: отметка `cron:bk` (`SET NX PX`), между проверками `skipped`, `reason:'recent'`; `partial` отметку снимает, после ошибки она остаётся (повтор через 6 часов); ошибка настройки отмечается в каждом запуске (ключ проверяется без сети).
- `backupIfDue`: есть незаконченная копия — продолжает её; иначе новая только если последней полной больше 7 суток (`DUE_GAP_MS`), иначе `{state:'skip'}`. Номер копии берётся в её начале, поэтому ровно через 7 суток проверка может ещё ответить `skip`, и копия сдвинется на следующую проверку.
- Код ответа cron 502 при ошибке копии (`state:'error'`, в ответе только `kind`: `config`, `key`, `format`, `tamper`, `missing` или имя ошибки SDK; текст — в журнале Vercel) и при `partial` в последнем запуске дня (час 23 по Москве); иначе 200. Сбой копии не отменяет отправленные напоминания.
- Нет `BACKUP_KEY` (не задан или пуст) — `{state:'off'}`, 200 (деплой до создания ключа безопасен; `off` — функция не видит переменную: имя, окружение Production, новый деплой). Ключ задан, но негоден (не 64 hex, кавычки, пробелы, слишком простой) — `error`, `kind:'config'`, 502: опечатка не должна молча выключать копии. Ключ есть, Blob не подключён — ошибка записи, 502.
- Ручной `/api/cron?backup=1` (с `CRON_SECRET`): только копия, без рассылки; продолжает незаконченную или начинает новую независимо от давности; 400 при пустом ключе, 502 при ошибке, при `partial` 200 (повторить после паузы больше 45 с); отметку и замок не трогает. `?backup=1&dry=1` и обычный `?dry=1` показывают `{state:'on', blob, copies, last, running, due}` без расшифровки и записи.
- Поля `backup` в ответе: `state` (`done`, `partial`, `skip`, `busy`, `skipped`, `off`, `error`), `ms`, `snap`, `parts`, `keys`, `bytes`, `pruned`, `stats` (`scanned`, `copied`, `gone`, `changed`, `foreign`, `temp`, `other`); ключей и содержимого записей нет.

## Восстановление (`scripts/restore-backup.mjs`)
- Разовый скрипт (не функция Vercel; нужны `npm i`, `KV_REST_API_URL`, `KV_REST_API_TOKEN`, `BLOB_READ_WRITE_TOKEN`, `BACKUP_KEY`, значения только в окне PowerShell); по умолчанию сухой прогон. Запускает владелец.
- Режимы: `--list` (копии; нечитаемые под другим ключом помечены; Redis не нужен), `--verify` (новейшая или `--snap=<номер>` целиком: шифр, sha, записи; ничего не пишет; Redis не нужен), без флагов (сухой прогон: сколько ключей создастся и перезапишется), `--apply` (запись; подтверждение вводом `RESTORE PROD` при любой записи, кроме `--drill`; `--yes` отключает вопрос; пустой префикс только предупреждает), `--drill` (копия разворачивается в одноразовый префикс `drill<время>:`, сверяется и удаляется; боевая база не затрагивается; занятый префикс — отказ).
- Куда: `DB_PREFIX` процесса или `--to=<префикс>`; что: новейшая полная копия или `--snap=`. Виды `rl` и `tgt` по умолчанию пропускаются (это для старых копий), `--all` возвращает всё, `--skip=a,b` — свой список пропуска.
- Порядок: копия проверяется целиком (`verifyBackup`), при любой проблеме не пишется ничего (`mode:'refused'`); затем план (`EXISTS` по ключам), подтверждение, запись частями до 200 КБ (`restoreCmds`), после каждой части ключи читаются и сверяются (`compareRecs`: тип, значение независимо от порядка полей, срок жизни). Ключи, которых нет в копии, не трогаются; ключ другого типа или с лишними полями заменяется.
- Код выхода: 0 при успехе и отмене, 2 при повреждённой копии или расхождениях, 1 при ошибке настройки, Redis или Blob. В выводе только числа, виды ключей и номер копии.
