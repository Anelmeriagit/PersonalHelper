# Резервная копия Redis (этап 4)

Читать при правках `api/_backup.js`, запуска копии из cron (4.3), скрипта восстановления (4.4), ключа `BACKUP_KEY`. Общие ограничения и карта файлов — в `PROJECT_NOTES.md`.

## Решения владельца
Копируем всё (все ключи Redis); раз в сутки автоматически внутри cron (вечерний вызов) плюс ручной запуск `?backup=1`; хранить 7 копий; шифровать ключом `BACKUP_KEY` (AES-256-GCM); нужен скрипт восстановления с проверкой. Этапы: 4.1 ядро, 4.2 Blob, 4.3 cron (сделаны), 4.4 восстановление, 4.5 заметки и проверки на настоящих базах.

## Ядро (4.1)
- `readBatch(cursor, {count})` → `{recs, cursor, done, stats}`: SCAN `MATCH <префикс>*` (префикс `DB_PREFIX` экранируется), типы `string`, `hash`, `set` читаются пачками (`TYPE`+`PTTL`, затем `GET`/`HGETALL`/`SMEMBERS`). Другие типы (list, zset) пропускаются и считаются в `stats.other`. Если тип ключа сменился между чтением типа и значения, ключ считается `changed`; пропавший — `gone`. Сеть и прочие сбои — ошибка наружу, пустой копии не бывает.
- При пустом префиксе (бой) пропускаются ключи тестового проекта (`SKIP_PREFIXES`: `t:`, `selftest`), иначе они попали бы в боевую копию; они считаются в `stats.foreign`.
- Запись: `{k, t:'s'|'h'|'e', v, ttl?}`; ключ без префикса (копию боя можно развернуть в `t:`), хэш парами `[[поле, значение]]`, `ttl` — оставшиеся миллисекунды. Размер записи — `recSize`.
- Шифрование: `seal`/`open` (AES-256-GCM, новый iv на каждую часть). Файл: `PHB1` | id ключа (4 байта sha256 ключа) | iv (12) | тег (16) | шифртекст. Заголовок и `snap|n` входят в AAD: часть нельзя переставить в другую копию или номер. Ошибки `BackupError.kind`: `config` (нет или слабый `BACKUP_KEY`), `format`, `key` (другой ключ), `tamper` (изменён), `missing` (нет файла), `busy`.
- `BACKUP_KEY`: ровно 64 шестнадцатеричных символа, не менее 8 разных. Потеря ключа = копии не расшифровать; смена ключа делает старые копии нечитаемыми (список покажет `error:'key'`).
- Часть = `encodePart({snap, n, recs})` = gzip(заголовок `{v,snap,n,at,prefix,count}` + по записи на строку) → `seal`. `decodePart` проверяет шифр, версию, номер копии и части, форму каждой записи, число записей, предел распаковки `MAX_PLAIN` (64 МБ).
- Восстановление записи: `restoreCmds(rec, префикс)` → `DEL`, затем `SET`/`HSET`/`SADD`, затем `PEXPIRE`. Префикс назначения свой (проверка в `t:`).
- Ограничения: SCAN не атомарен (ключ, записанный во время обхода, попадёт в старой или новой версии, повторы ключей возможны, при восстановлении побеждает последняя запись); документы версионируются (CAS), поэтому копия ключа сама по себе целостна. Копируются и временные ключи (`rl:`, `tgt:`) со сроком жизни.

## Хранение в Blob (4.2)
- Единственное место в `api/`, где используется Blob (`import('@vercel/blob')` при первом обращении, пакет в `package.json`). Приватный доступ, всё зашифровано; открытыми остаются только имена файлов. Redis копия не пишет.
- Раскладка (папка `backup/`, для проверок `BACKUP_DIR`): `backup/<копия>/p<n>.bin` (части), `backup/<копия>/manifest.bin` (манифест, зашифрованный JSON: `v`, `snap`, `at`, `end`, `prefix`, части `{n, bytes, count, sha}`, `keys`, `bytes`, `stats`), `backup/progress.bin` (ход). `<копия>` = `20261005t180000-ab12` (время UTC до секунды и 4 hex-символа; по алфавиту = по времени).
- Копия считается полной, только когда записан манифест (он пишется последним). Часть: `PART_BYTES` = 1 МБ открытого текста.
- `runBackup({budgetMs, count, partBytes, keep, now})` → `{state:'done', snap, parts, keys, bytes, stats, pruned}` | `{state:'partial', snap, parts, keys}` (бюджет `BUDGET_MS` = 22 с кончился, повторить вызов) | `{state:'busy'}` (копию ведёт другой запуск). Ошибки (`config`, сбой Redis или Blob) выбрасываются наружу.
- Ход `progress.bin` (зашифрован, AAD `progress`): `{snap, at, upd, cursor, done, n, parts, stats}`; пишется после каждой записанной части. Он же замок: создаётся с `allowOverwrite:false`, обновляется с `ifMatch` (ETag). Свежий ход (младше `LEASE_MS` = 45 с) = занято (`busy`); старше — продолжается с курсора. Ход старше `STALE_MS` = 20 ч бросается вместе с частями (копия должна быть из одного дня). Ход, который нельзя прочитать (другой ключ, порча), заменяется. Если манифест уже записан, а ход остался, ход удаляется и копия начинается заново. Сбой записи части не сдвигает ход: повтор доделывает.
- Ротация `pruneBackups(keep = 7)`: остаются `keep` самых новых полных копий (не меньше одной), прочие удаляются целиком; неполные копии, не принадлежащие текущему ходу, удаляются; чужие файлы в Blob не трогаются. Вызывается в конце удачной копии. Ротация считает копии по манифесту, а не по ключу: копии под старым ключом тоже входят в 7.
- `listBackups()` → `[{snap, complete, at, end, keys, parts, bytes, prefix, error?}]`, новые первыми. `readManifest(snap)`, `readPart(snap, manifest, n)` (проверяет размер и sha из манифеста, потом шифр), `verifyBackup(snap)` → `{ok, snap, parts, keys, problems}` (без содержимого записей и секретов).
- Проверка на настоящих базах: `tests/live-blob.mjs` (папка `backup-selftest-<время>/`, префикс `selftest<время>:`, одноразовый ключ; в конце удаляет созданное). Тесты: `tests/backup.test.mjs` (ядро), `tests/backup-blob.test.mjs` (Blob).
- Номер копии точен до секунды: две копии в одну секунду упорядочиваются случайно. При запуске раз в сутки неважно.

## Запуск из cron (4.3, `api/cron.js`)
- Копия идёт **в оба слота** (дневной 11:00 UTC и вечерний 15:00 UTC), после рассылки напоминаний, на оставшееся время: бюджет обхода `min(20 с, 30 с − уже потрачено − 8 с запаса)`, меньше 3 с — копия пропускается (`skipped`, доделает следующий слот). Решение вместо «только вечером»: третьего cron-вызова на Hobby нет, а так сбой или нехватка времени днём доделываются вечером (4 часа спустя, ход живёт 20 ч).
- По расписанию вызывается `backupIfDue`: если есть незаконченная копия (`progress.bin`), продолжает её; иначе делает новую, только если последней полной больше 20 часов (`DUE_GAP_MS`), иначе `{state:'skip'}`. Поэтому в сутки получается одна копия.
- Код ответа cron: 502 при ошибке копии (`state:'error'`, в ответе только `kind`: `config`, `key`, `format`, `tamper`, `missing` или имя ошибки SDK; текст ошибки только в журнале Vercel) и при `partial` в вечернем слоте (следующая попытка только завтра). `partial` днём — 200. Сбой копии не отменяет уже отправленные напоминания.
- Нет `BACKUP_KEY` — `backup:{state:'off'}`, код 200 (деплой до создания ключа безопасен). Ключ есть, а Blob не подключён — ошибка записи в Blob → 502.
- Ручной запуск: `/api/cron?backup=1` (с `CRON_SECRET`): только копия, рассылка не идёт; продолжает незаконченную или начинает новую независимо от давности последней; 400 при пустом `BACKUP_KEY`, 502 при ошибке, при `partial` код 200 (вызвать ещё раз после паузы больше 45 с). `/api/cron?backup=1&dry=1` и обычный `?dry=1` показывают состояние: `{state:'on', copies, last (ISO), running, due}` без расшифровки и записи.
- Поля `backup` в ответе: `state` (`done`, `partial`, `skip`, `busy`, `skipped`, `off`, `error`), `ms`, `snap`, `parts`, `keys`, `bytes`, `pruned`, `stats`. Ключей и содержимого записей в ответе нет.
- Тесты: `tests/cron-backup.test.mjs`.
